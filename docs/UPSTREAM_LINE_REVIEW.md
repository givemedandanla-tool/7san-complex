# 原版角色邀約腳本逐行審查

審查基準是使用者指定的 [柒葉子「七聖召喚角色邀約全自動」main.js，固定提交 9756c1b6608eec84515dac63e2517b1fd6266af4](https://github.com/babalae/bettergi-scripts-list/blob/9756c1b6608eec84515dac63e2517b1fd6266af4/repo/js/%E4%B8%83%E5%9C%A3%E5%8F%AC%E5%94%A4%E8%A7%92%E8%89%B2%E9%82%80%E7%BA%A6%E5%85%A8%E8%87%AA%E5%8A%A8/main.js)。本專案保存的完整原文是 `vendor/invitation/main.js`，共 197 行；以下行號全部指這份上游原文，不是產生後的接入層。

以下結論來自原始碼與操作順序，不代表已在原神／BetterGI 會話實測。畫面上的鎖定頁籤如何回應點擊，必須區分使用者已觀察到的行為與程式明確執行的辨識。

## 兩項回報的核對結果

### 邀請函數量填 0

原版第 4 行的欄位代表「持有邀請函數量」，原設定標籤還寫明「已邀請角色也算」。第 183 行的條件是 `letterNumber <= i`，而外層第一輪 `i = 0`。因此輸入數字 `0` 或字串 `"0"`，原版都會在第一輪傳送後先購買一張；`0` 本身沒有「禁止購買」的意思。

v0.2.0 的 `config()` 透過 `Number(value)` 保留數值 0，再把它傳給由原版產生的外層循環。因此「填 0 仍先購買」是原版條件的結果，不能歸因為新版把 0 當成空值。若現在要讓 0 表示不自動購買，必須明確新增購買政策或改變欄位語意，並寫清楚這與原版條件的差別，不能宣稱原版原本就如此。

可直接代入原版條件重現：

| 持有數 | 挑戰輪數 | 購買發生在哪一輪 |
|---|---:|---|
| `0` | 1 | 第 1 輪，因為 `0 <= 0` |
| `0` | 3 | 第 1、2、3 輪；每次購買後持有數加 1 |
| `1` | 3 | 第 2、3 輪 |
| `2` | 3 | 第 3 輪 |

這是依使用者填寫數量進行的排程，原版沒有讀取遊戲中實際庫存，也不判斷目前目標是否已邀請。

### 認真勝負未解鎖時停止

原版第 68 行只固定點擊 `(1435, 224)`，註解為「選擇認真勝負」；等待後直接執行第 70 行 `(1443, 875)` 的開始點擊，再執行第 72 行確認。**這份固定版本沒有讀取鎖頭圖案、沒有判斷認真勝負是否解鎖，也沒有難度鎖定時拋出例外的分支。**

使用者觀察到原版在認真勝負未解鎖時，仍停留友好對局並點「邀約對局」。這與上述程式相容：若遊戲忽略對鎖定頁籤的點擊，原版會繼續執行開始點擊。這是遊戲頁籤狀態配合原版操作產生的行為，不能說成原版明確辨識了鎖頭。

v0.2.0 有可確認的偏差：

1. `tools/build.py` 在原版第 70 行之前拆開 `chooseCharacter()`，形成選角與開始兩段。
2. `OriginalFlow.challenge()` 在這兩段之間呼叫 `ui.verifyOriginalSelection()`，再呼叫 `ui.selectDeck()`。
3. `verifyOriginalSelection()` 與 `selectDeck()` 都要求已經辨識到「我方出戰牌組／出戰牌組」的準備頁。
4. 但原版此時只走到第 69 行，原本第 70、72 行的「邀約對局／確認」尚未執行。若畫面仍是使用者提供的友好對局邀約詳情，這個新增前提便會提前停止原本可繼續的流程。

因此不能只驗證「把新增檢查省略後的按鍵序列相同」，便宣稱整合後與原版行為一致。原測試中，操作軌跡比對使用的 `challenge` 回呼直接執行選角、開始、打牌；另一組外層流程測試又把 `verifyOriginalSelection()` 與 `selectDeck()` 替換為簡化模擬，未涵蓋這個實際頁面次序。

最小修正方向是保留原版完整 `chooseCharacter()` 操作，在原第 70 行點擊之前、原第 72 行點擊之前，以及進局前對話的觀察點，僅在**實際辨識到可換牌組的準備頁**時接入換牌組。當仍處於友好對局的邀約詳情時，繼續原操作，不把缺少準備頁標記視為失敗。不能只把換牌組固定搬到原第 80 行之前：如果當時已進入初始手牌，便已錯過切換時機。若直到牌局開始仍未確認選中指定牌組，應清楚停止，不能假設換牌已成功。

這份原碼只把第 70 行註解為「開始」、第 72 行註解為「確認」，並未說明確認的具體視窗。**不能僅憑座標假定 `(1175, 754)` 一定是消耗邀請函、邀請角色或開局確認中的某一種。** 觀察點應依當時辨識出的畫面決定是否接入，而非把未知視窗預先分類。

如果準備頁是在後續對話中才出現，該觀察點需先完成換牌與準備頁上實際可見的開始操作，再交牌手。BetterGI 固定策略的 `CommonDuelPrepare` 處理的是初始手牌，不能據此假設它會替腳本按挑戰準備頁的開始按鈕。這也應以本專案已保存的七日歷練流程（對話後換牌組、再按開始）作為另一種可到達時機的回歸情境。

若保留難度辨識，應容許友好頁籤可用而認真頁籤鎖定；不能把「未解鎖認真勝負」當成整體無法開局，也不能只憑頁籤文字存在就宣稱它已被選中。具體畫面轉換仍須由回歸模擬及實際會話分別驗證。

## 0.4.3：這次確定漏掉的是 NPC 調整卡組入口

本次七份附件是 **0.4.2**，不是前一次的舊版本問題。原「確認前」畫面只有 `迪希雅受邀前来进行牌局··`，沒有可辨識的確認按鈕；之後的對話畫面右上角明確顯示 `当前牌组：我的牌组`（標籤約 `(1640,38)`）。再下一階段已是 NPC 接受對局的台詞、VS 載入、初始手牌。這些資料證實角色邀約走了 NPC 對話；它並非前版當作唯一入口的七日歷練準備頁。

使用者另提供截圖與操作說明：需先點「先调整一下卡组…」進入卡組一覽，回到最左，再逐段找牌組。0.4.2 雖有讀取牌組名稱的功能，但沒有這個入口；「每次按鍵前重新觀察」仍把 NPC 對話視為一般對話，沒有阻止預設開局。先前離線測試只有準備頁在確認或按鍵間出現的情境，未涵蓋本次入口，這是上次修補仍漏掉的原因。附件不足以把每次預設選擇精確歸因於固定滑鼠點擊或 F 中的某一個，所以兩處都加入實際狀態判斷。

本版接入方式：

1. 原選角函式仍完整生成；原開始及確認座標保留，加入回傳值判斷。受邀進場後先等到可辨識的對話／準備／確認／開局畫面，不以「任意非空 OCR」當作轉場完成。若接管了 NPC 邀約對話，才替代該次舊固定點擊。
2. 對話一進入即觀察，另保留每輪及每次空白鍵、F 前觀察。看到右上角當前牌組或明確選項時接管，等待調整選項而不按預設鍵；點「先调整一下卡组」後才處理一覽。
3. 向右按住滑鼠分步拖動，每次等待至少三次名稱／位置穩定，連續兩次完成拖動後首個名稱及清單位置不變才確認左端。不是固定拖幾次便假定成功，也不把空白 OCR 視為邊界；無法確認時停止。
4. 從左端以約 320 像素向左重疊拖動搜尋，名稱與位置每段都讀；`deckPages` 仍控制搜尋範圍，每頁約四組。舊設定的整頁拖動座標不會變成這個小拖動。卡片部分偏移時優先使用整頁 OCR 的實際文字位置，局部四格 OCR 保留作回退。
5. 選擇後等待 4 秒，回 NPC 對話重新確認右上角牌組名稱，再點明確的「進行七聖召喚的對局吧」選項。只有選好並開始後的正常接受台詞才交回原對話按鍵；賽後掛鉤仍停用。缺少調整選項、名稱不符、辨識錯誤皆不默認開始。

沒有改寫四套牌手、原購函排程、兩段順序或賽後續跑。新增的整合模擬使用附件中去除 UID／玩家姓名的必要 UI 文字，覆蓋進場部分文字、NPC 對話、中段起始、1600 毫秒拖動延遲、卡片偏移、非首屏名稱與輸後換策略；另驗證錯名、缺少選項、無法讀名、所有牌組缺失時不開局。這些是離線驗證，不是遊戲會話實測。
