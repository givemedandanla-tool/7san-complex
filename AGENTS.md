# Development guidance

This repository extends the pinned original BetterGI invitation script with four players, named decks and ordered fallback. The user explicitly requires the original navigation, purchasing schedule, two legs per round and outer-loop continuation. Work in the existing checkout; do not create a Git worktree unless explicitly requested.

- Read `README.md` and `src/InvitationFallback/README.md` before changes.
- Keep both routes: the existing BetterGI txt executor and the four upstream recognition players. Do not rewrite their decisions or recognition thresholds.
- `vendor/` is an immutable pinned input; hashes are in `vendor/lock.json`. Build invocation adapters in `tools/build.py`, rather than editing generated or vendored modules.
- BetterGI runs ClearScript V8, not Node. Use only verified host APIs and bundled local resources in runtime JS. Do not add runtime network requests.
- Use `tools/build.py` to generate the navigation adapter from the pinned original script. Keep `chooseCharacter()` whole, including its original start and confirm clicks; observe actual readiness without splitting the function or demanding a preparation page before invitation. Do not require a typed opponent, difficulty or manual preparation-page entry.
- The pinned original has no explicit lock recognition: a click on a locked serious tab can leave friendly selected. Preserve that valid path. Only select a deck on an observed preparation page and finish before entering opening cards. Gate all readiness hooks off during post-game dialogue.
- Preserve the selected invitation panel across retries. Only a confirmed loss can select a fallback. Errors, cancellation, unknown results and resource failures are separate outcomes. Each leg starts from the first configured strategy again.
- After all played strategies lose and original result exit/dialogue has completed, record the leg as lost and continue the original outer loop; do not declare it won. Missing all remaining decks stops execution on preparation even if an earlier attempt lost; never walk to the next leg while still in a menu. A technical error stops execution.
- Do not repeat invitation purchases or consuming invitations from a retry loop. Record and stop on an unverified purchase.
- The user clarified bug 1 was a misunderstanding: restore the exact original `letterNumber <= i` purchase schedule without an `autoBuy` toggle. The input label must be exactly `持有邀請函數量（已邀請角色也算）`. Zero triggers the original first-round purchase. Ignore any saved obsolete `autoBuy` value. Preserve purchase verification and the pending journal; do not add purchasing inside retries.
- Smart-player `maxMinutes` is a manually entered positive integer, default 15; 120 must reach the actual player deadline. Keep vendor bodies immutable and adapt the upstream menu whitelist at the factory boundary. Preserve upstream timeout exceptions, action limits, and cleanup. This setting covers one smart-player game, not native text strategies or navigation/UI waiting.
- Review actual game-stage boundaries in addition to input traces. Regression tests must use real UI/flow modules with invitation pages lacking deck controls, a locked serious tab, readiness after confirmation/dialogue, and no unverified play. `docs/UPSTREAM_LINE_REVIEW.md` documents all 197 original lines and the previous missed boundary.
- No running game session has been tested in this cloud environment. Do not describe simulated UI tests as game validation.
- Run `npm run build`, `npm test`, and `npm run check` after changes. Node 22+ and Python 3.10+ are sufficient; there are no npm package dependencies.
- The user-facing deliverable uses the version in `src/InvitationFallback/manifest.json`: `dist/InvitationFallback-<version>.zip`, with an identical copy in `downloads/`. Keep the ZIP checksum current. The user has authorized uploading this implementation to the existing GitHub repository.
