# Development guidance

This repository extends the pinned original BetterGI invitation script with four players, named decks and ordered fallback. The user explicitly requires the original navigation, purchasing schedule, two legs per round and outer-loop continuation. Work in the existing checkout; do not create a Git worktree unless explicitly requested.

- Read `README.md` and `src/InvitationFallback/README.md` before changes.
- Keep both routes: the existing BetterGI txt executor and the four upstream recognition players. Do not rewrite their decisions or recognition thresholds.
- `vendor/` is an immutable pinned input; hashes are in `vendor/lock.json`. Build invocation adapters in `tools/build.py`, rather than editing generated or vendored modules.
- BetterGI runs ClearScript V8, not Node. Use only verified host APIs and bundled local resources in runtime JS. Do not add runtime network requests.
- Use `tools/build.py` to generate the navigation adapter from the pinned original script. Keep `chooseCharacter()` whole with its original coordinates. The start/confirm hook may replace its old fixed click only when it has positively observed and handled the actual NPC invitation dialogue. Wait through the observed `受邀前来进行牌局` arrival until a recognized dialogue/preparation/confirmation page, never just any nonempty OCR frame. Do not require a typed opponent, difficulty or manual preparation-page entry.
- The pinned original has no explicit lock recognition: a click on a locked serious tab can leave friendly selected. Preserve that valid path. Select through an observed preparation page or the confirmed NPC adjustment/list route and finish before opening cards. Gate all readiness hooks off during post-game dialogue.
- Do not classify a game opening from generic `出战角色` or `重投` anywhere on screen. Use the upstream player's verified header/prompt/button ROIs and exclude invitation, deck chooser and editor pages. An invitation may contain a character preview using those same words.
- The reported logs with no before-invite files are version 0.4.0, and their OCR really is the initial hand. Do not reinterpret that report as the 0.4.1 preview false positive or demand nonexistent files. Log the active script version. Reuse the pinned weekly script's local name ROIs (1305,793,206,46 and four slots at 135+463*i,762,230,46), narrow OCR corrections and 4000ms post-selection wait. Observe preparation before each pre-game dialogue SPACE/F as well as at the loop start; keep those hooks inactive after the game. The uploaded log does not establish which intermediate page was missed; distinguish the simulated key race from a proven user-session cause. Never commit uploaded UID rows.
- Weekly preparation and co-op invitation controls do not establish the character-invitation layout. When an entry is unverified, collect the actual before-start/before-confirm OCR or screenshot instead of inventing a modal layout or claiming a hypothetical flow is game-verified. Checkpoints are saved locally as `data/before-invite-start.*` and `data/before-invite-confirm.*`; respect the existing diagnosticImages option.
- The latest reported 0.4.2 route is now identified: arrival notification, NPC dialogue with top-right `当前牌组` at (1640,38), then an unprepared initial hand. The user's screenshots establish the `先调整一下卡组` entry. Own this pre-game dialogue; never let its unprepared state fall through to default SPACE/F. Click adjustment, enter the list, drag right until the first name/list/positions stay stable across two completed drags, then search with overlapping small leftward drags. Empty OCR is a technical error, not an edge. Recheck the top-right deck after selection and before clicking the explicit duel option. Use full-frame text positions for partially scrolled cards and local name ROIs as fallback. The prior tests omitted this NPC entry; retain the sanitized report fixture and actual UI/flow/navigation integration tests.
- Preserve the selected invitation panel across retries. Only a confirmed loss can select a fallback. Errors, cancellation, unknown results and resource failures are separate outcomes. Each leg starts from the first configured strategy again.
- After all played strategies lose and original result exit/dialogue has completed, record the leg as lost and continue the original outer loop; do not declare it won. Missing all remaining decks stops execution on the same NPC dialogue/preparation even if an earlier attempt lost; never walk to the next leg while still in a menu. A technical error stops execution.
- Do not repeat invitation purchases or consuming invitations from a retry loop. Record and stop on an unverified purchase.
- The user clarified bug 1 was a misunderstanding: restore the exact original `letterNumber <= i` purchase schedule without an `autoBuy` toggle. The input label must be exactly `持有邀請函數量（已邀請角色也算）`. Zero triggers the original first-round purchase. Ignore any saved obsolete `autoBuy` value. Preserve purchase verification and the pending journal; do not add purchasing inside retries.
- Smart-player `maxMinutes` is a manually entered positive integer, default 15; 120 must reach the actual player deadline. Keep vendor bodies immutable and adapt the upstream menu whitelist at the factory boundary. Preserve upstream timeout exceptions, action limits, and cleanup. This setting covers one smart-player game, not native text strategies or navigation/UI waiting.
- Review actual game-stage boundaries in addition to input traces. Regression tests must use real UI/flow modules with invitation pages lacking deck controls, a locked serious tab, readiness after confirmation/dialogue, and no unverified play. `docs/UPSTREAM_LINE_REVIEW.md` documents all 197 original lines and the previous missed boundary.
- No running game session has been tested in this cloud environment. Do not describe simulated UI tests as game validation.
- Run `npm run build`, `npm test`, and `npm run check` after changes. Node 22+ and Python 3.10+ are sufficient; there are no npm package dependencies.
- The user-facing deliverable uses the version in `src/InvitationFallback/manifest.json`: `dist/InvitationFallback-<version>.zip`, with an identical copy in `downloads/`. Keep the ZIP checksum current. The user has authorized uploading this implementation to the existing GitHub repository.
